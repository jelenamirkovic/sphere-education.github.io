Overview

This exercise proposes an extension to the Internetworking Lab that incorporates the installation, configuration, and testing of IPSec, along with extra credit to encourage the student to go beyond and set up a more robust IPSec tunnel.

Introduction

The internetworking Deter Lab the class did is an excellent introduction to how the internet functions. However, it may be easily extended to also include an exercise on the configuration of IPSec for both a computer-to-computer tunnel, as well as a full mesh configuration where all nodes int the simulated internet talk to each other via IPSec tunnels.

Required background reading

  • IPSec Host-to-Host VPN on Ubuntu 14.04
  • Red Hat Linux Host-to-Host IPSec Configuration

Assignment Instructions

Setup

Go ahead and swap in your experiment using /share/education/IPSec_USC/internetworking-with-ipsec.ns topology file. IP addressing will be done for you automatically, unlike in the internetworking exercise. You will only need to configure routing so that the nodes can talk to each other. As our initial method for enabling IPsec won’t be able to deal with NAT, leave it alone for now. For now, just configure routes such that all nodes can “see” each other. Please read all the background material before you begin.

Tasks

Getting Started

Our objective is to establish an IPSec tunnel between the two workstations in our “internet”. While manual configuration is possible, it may involve significant hair loss, so we will use tools available in the Ubuntu repositories to set up our tunnel. Initially, we will use pre-shared keys to establish the tunnel.

Intercepting Traffic

Try generating some traffic and intercepting it. What can you find out about that traffic? Answer question 1 below.

Installing Tools

Go ahead and access both of the workstations via ssh. You’ll need to install the tools on both nodes with the following command:

apt-get install ipsec-tools strongswan-starter

Getting the Tunnel Up

Follow the instructions given here, making sure to replace their IP addresses and information in the commands with yours: https://www.gypthecat.com/ipsec-vpn-host-to-host-on-ubuntu-14-04-with-strongswan

As long as you have working routes, you should be able to successfully configure a tunnel between the two workstations! Now, try intercepting traffic again. Answer question 2 below.

Extra credit

Previously, we successfully set up a tunnel between two hosts, but we didn’t have to deal with traversing NAT. The first step will be to perform all the setup steps again (we recommend a freshly swapped in instance of your experiment, to ensure that any MITM you did above doesn’t cause any problems with configuration), so that all of the infrastructure (including NAT) is set up.

NAT Traversal

Now, with NAT configured, work on setting up the tunnel again. You’ll need to figure out how to deal with NAT traversal.

IKE and raccoon

For extra bonus points, instead of using pre shared keys, configure a tool called raccoon to automatically key your IPSec clients using the Internet Key Exchange (IKE) protocol.

Full Mesh

Extend the raccoon setup to configuring a full mesh VPN. That is, configure all the nodes of the network to only talk to one another over IPSec tunnels.

Submission Instructions

Submit the answers for the following questions:
  1. How much traffic could you read when you intercepted before IPSec was enabled? There’s no one right answer here.
  2. What happened to your intercepts after you configured the IPSec tunnel (if all goes well, you shouldn’t be able to read any data sent!)
  3. (extra credit) What are the steps needed to deal with NAT traversal?
  4. (extra credit) How do you configure raccoon to handle the keying automatically?
